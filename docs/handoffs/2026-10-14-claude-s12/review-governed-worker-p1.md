## Security
- Ordering (`routes.ts:82-127`): origin → media/JSON preflight → CSRF → bounded body read → verified session →
  query-string refusal → strict body → acting party + `any_of` capability → user quota → party quota → header
  validation (finding 2) → abort check → port. The production port re-proves identity and capability on the original
  `Request` object before the RPC (`production-governed-review.ts:70-110`; `refresh.test.ts:125-162` proves a cloned
  Request is refused 401).
- Concealment: the Worker deliberately gates only `any_of`; subject visibility and the per-kind capability stay in
  SQL under the authority locks (SQL:78-101), so a hidden subject is 404 and a visible one without the kind's
  capability is 403, with byte-identical 404 bodies (`refusals.test.ts:50-61`). Correct per 1467.
- Leakage: messages are catalog-bound; `details` are projected through allowlists (`response.ts:66-112`); attacker
  member names never echoed (`submit.test.ts:114-140`); caller `x-actor-id`/`x-capabilities`/`x-owner-party-id`
  never reach the wire (`production.test.ts:18-52`); prose in DETAIL never selects a refusal
  (`refusals.test.ts:155-172`); telemetry carries requestId/status/outcome/duration only.
- Bounds: 262,144-byte request and response caps, tighter configured budget honoured, minimum error-envelope guard.
- Idempotency: key mandatory; SQL reserves late and replays the stored body; the Worker never retries a mutation.
- CAS/MFA: none by spec (215, 216); a present `If-Match` is refused.
- SQL grants (read-only check): `300810:37-39` revokes from public/anon/authenticated/service_role then grants
  EXECUTE to `service_role` only; the Worker calls with the service secret (`rpc.ts:131`).
- The `p_request` key set `{subjectKind, subjectId, subjectHash, context, idempotencyKey, correlationId}` matches
  `cms_exact_keys` (SQL:57-61) exactly (`submit.test.ts:65-72`), and the server-built `context` carries the keys the
  SQL identity helpers read: `cfg_actor` reads `context.authUserId`/`context.actorPersonId` and `cfg_acting_party`
  reads `context.actingPartyId` (`supabase/migrations/20260901070000_platform_configuration_authority.sql`), all
  emitted by `cmsEditorialContextFor` (`cms-editorial-production-session.ts:69-96`; `admission.test.ts:49-63`).

## Rulings on the author's open questions (which layer is wrong per spec; minimal correct fix)

**(1) SQL `pattern_version_not_active` on submit (SQL:153-160) — SQL is wrong; contract and Worker are right.**
BE03c 1304 scopes that token explicitly: "`pattern_version_not_active`, `pattern_incompatible` and
`nested_pattern_not_active` are 422 on CMS-03C-02, CMS-03C-12 and CMS-03C-15 (a pattern version a request names as an
input that is not `active` fails validation)", and DEC-180 R5 (`.memory/wiki/decisions.md:2593-2612`) gives the
reason: "`nested_pattern_not_active` and `pattern_version_not_active` are 422 (request validation; 409 stays for
stale CAS operands)". The CMS-03C-06 request names no pattern version (`governed-review.ts:54-58`); the nested
pattern is a stored dependency of the subject, so nothing in the request is being validated. The 06 error-matrix row
(1259) lists only `subject_not_submittable` under 409 and "subject hash/kind failure, canonical_source_unavailable"
under 422; the machinery table's `pattern_version` row (1313) states the submit precondition "every nested pattern is
`active`, compatible and acyclic" with no token of its own, and 389 gives the precondition token for 06:
"else 409 `subject_not_submittable`". SQL already uses that token for the sibling preconditions in the same branch
(digest, line 163; bound types, line 171). The contract list `refusals.ts:144-149` is therefore correct and must not
be widened (frozen; widening would contradict 1304), and the Worker's scrubbed 500 for an out-of-list token is the
1298-1302 behaviour. Minimal fix: a forward migration in the SQL lane's timestamp range (never edit `300820`)
re-creating `platform_private.cms_submit_governed_review` with line 159's token replaced by
`subject_not_submittable`, plus a pgTAP case submitting a `pattern_version` whose nested pattern is not `active`
(none exists today, finding 6). No Worker change.

**(2) `canonical_source_unavailable` without `details.domain` (SQL:142-152) — SQL is wrong; the Worker already
consumes the fix.** BE03c 1375 ("422 `GOVERNED_REVIEW_VALIDATION_FAILED` with `details.reasonCode`
`canonical_source_unavailable` and `details.domain`, DEC-180 G11"), the machinery table's `taxonomy_version` row
(1314, "else 422 `canonical_source_unavailable` with `details.domain`"), the testing line 1611 ("422 with
`details.domain`"), FE03 1115 ("the message names `details.domain`, DEC-180 G11") and the contract
(`refusals.ts:257-263`, `domain` required) all require the member; SQL raises with no DETAIL. Minimal fix: forward
migration replacing lines 145-152 with a select of the first unbuilt domain in the version's declared order into a
local and `raise exception 'canonical_source_unavailable' using errcode = 'P0001', detail =
pg_catalog.jsonb_build_object('domain', v_domain)::text`, plus a pgTAP case for a `taxonomy_version` declaring an
unbuilt domain asserting the DETAIL. The Worker parses exactly that DETAIL (`rpc.ts:49-62,93-100`;
`refusals.test.ts:92-105`). Whether the Worker keeps its domain-less fallback or fails closed is finding 3.

**(3) Stored-hash mismatch: 422 at `/subjectHash` (spec 389) vs SQL 409 `subject_not_submittable` (SQL:127-130) —
SQL is wrong, and the author's "and its suite" claim is wrong (finding 6).** Three spec statements agree on 422:
389 ("`subjectHash` 64 lowercase hex equal to the stored `content_hash` (422 at `/subjectHash`); the subject state is
`draft` with no live review (else 409 `subject_not_submittable`)"), 1259 (422 column "subject hash/kind failure";
409 column "subject_not_submittable, idempotency") and FE03 1115 ("409 `subject_not_submittable`/415/422 hash
mismatch"). 1502 lists "draft, equal hash and no live review" as three preconditions without collapsing their
statuses; 215 makes the hash the subject-version identity but assigns no status. The only support for a 409 is by
analogy: DEC-180 R5 ("409 stays for stale CAS operands … the digest is an equality expectation the server recomputes
and refuses on mismatch") and DEC-186, but DEC-186 is scoped to `blockRegistryDigest` "on CMS-03C-01, CMS-03C-02 and
CMS-03C-12, no other member" (1304), and 06 has no CAS operand (215). SQL folds the hash inequality into the 409. Minimal fix: forward
migration splitting lines 127-130 — `state <> 'draft'` → `subject_not_submittable`; `contentHash <> subjectHash` →
`raise exception 'VALIDATION_FAILED' using errcode = 'P0001', detail = '["/subjectHash"]'` (the 03b pointer-array
DETAIL grammar, `cms-editorial-production-error-details.ts:64-89`; `/subjectHash` satisfies `SAFE_POINTER`,
`cms-editorial/error-vocabulary.ts:51`). The Worker needs no change: that raise already flows through
`mapCmsEditorialRpcFailure` → `rpc.ts:102-105` → `response.ts:107-110` to 422 `GOVERNED_REVIEW_VALIDATION_FAILED`
`{violations:[{path:'/subjectHash',code:'invalid',message:'The value is invalid.'}]}`. Add the pgTAP case (absent) and
the Worker test (finding 4c). If root prefers the 409 reading (hash as CAS operand), that is a spec change to 389,
1259 and FE03 1115 through `/propagate-decision`, not an SQL or Worker fix.
