### Q1 (architecture): what does a pattern placement store?

| Option | Pros | Cons |
|---|---|---|
| A. One row per root node of the pattern's forest, each pinned to `(patternId, patternVersion)` and carrying that root node's block identity with its node key as the path suffix; children stay inside the pinned tree; the 201 returns the list of rows (as `CompositionUpdateResource` already does, `items` 1-32) | Keeps one block per row, so the existing table, the D5 block comparison hash (BE03b:1704) and the render plan need no new concept; each row diffs and renders independently | Changes the CMS-03C-02 success shape from one resource to an items list; the instance list shows several rows per insertion |
| B. One row per request that stores the pattern reference with a nullable block identity (`block_key`, `block_version` NULL when `pattern_id` is set) | One row and one resource per insertion; matches the diff view (one pinned version per instance) | Relaxes two NOT NULL columns and the resource contract; the checker and render plan must expand the pinned tree (BE05c:1005 says only "composition order") |
| C. One row per request whose block identity is the first root node | No contract change | Arbitrary for forests of 2-32 roots; hides the other roots from comparison and rendering |

Recommendation: A. It is the only option that leaves the Slice 11 checker input, the D5 block comparison and the append-only table valid unchanged, and the success shape already has a precedent in CMS-03C-15.
