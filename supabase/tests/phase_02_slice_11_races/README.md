# Slice 11 independent-session race runners

N-session evidence for the Slice 11 editorial commands, in the repository convention of
`../phase_02_slice_10_races/README.md`: each runner drives fresh committed `psql` sessions inside the
disposable local database and proves an ordering or lock guarantee that a single pgTAP transaction cannot.
They are not Supabase-discovered tests; `infra/run-database-race-runners.mjs` (`pnpm db:races`) executes
every runner after a `pnpm db:reset`, and `RACE_RUNNERS` must list every `.mjs` here.

| Runner                             | Proves                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `010-review-assignment-race.mjs`   | `cms_assign_editorial_reviewer`: two creates of one reviewer commit one (`assignment_exists`, never a raw unique violation); with one slot left two creates for two reviewers commit one (`assignment_limit`, 16 rows); two revokes of one assignment commit one (`CONFLICT`); the command takes the review row lock (a create blocks behind a held `FOR UPDATE` and completes on release); the review version never moves.                                                                                                                                                                                                   |
| `011-review-decision-race.mjs`     | `cms_record_review_decision`: the review CAS (two approvals at one version commit one, the loser is `VERSION_MISMATCH` and retries to approval); approve vs reject; the same command twice at once replays; one reviewer under two keys commits one decision; the review row lock; authority revocation vs a decision parked after its authority locks (the revocation blocks, the decision commits, the revocation then invalidates the review; no deadlock) and a held grant-row lock blocking a decision; a decision vs the revoke of the reviewer's assignment (exactly one commits).                                     |
| `012-review-submit-race.mjs`       | `cms_submit_review`: two submissions of one revision commit one (`revision_not_submittable`); the same submission twice replays; the entry row `FOR SHARE` makes a revision append wait for an in-flight submit (the append then invalidates the review `revision_superseded`) and a submit wait for an in-flight append (`VERSION_MISMATCH`, no review).                                                                                                                                                                                                                                                                     |
| `020-preview-mint-race.mjs`        | `cms_mint_preview` and the preview-token revocation seams: the same mint sent twice at once answers one token (one row, one audit record, verifiable); one key with two bodies commits one (`IDEMPOTENCY_MISMATCH`); a mint parked after its locks blocks the minter's grant revocation, which then revokes the NEW token (no stale live token, no deadlock); a revocation holding its locks blocks a mint, which is then refused `capability_missing` with no token; a parked mint blocks the archiving of its entry, which then revokes the token.                                                                          |
| `013-schedule-claim-race.mjs`      | `cms_claim_due_publication_schedules`: four sweepers over twelve due schedules claim each exactly once (distinct leases, version 2); a schedule row locked by another session is SKIPPED, not waited for (`SKIP LOCKED`); expired leases are recovered exactly once by two concurrent sweepers (`failed_retryable`, one audit record) while a live lease is untouched; a worker holding the old lease is fenced out and the new lease completes once (one lineage row, one event); a schedule that crashes four times climbs the 15 s / 60 s / 300 s ladder and is blocked `retries_exhausted`.                               |
| `014-publication-execute-race.mjs` | `cms_publish_revision` / `cms_execute_publication_schedule`: one claimed schedule executed twice at once is `completed` + `already_completed` (one row, one event, one audit record); a manual and a scheduled publish of one lineage both commit as versions 1 and 2; two manual publishes under different keys commit 1 and 2, under one key they replay; a publish parked after its entry / authority locks blocks a revision append (then `revision_superseded`), an append holding the entry row blocks a publish (`VERSION_MISMATCH`), and an execution parked before its lineage insert blocks an append; no deadlock. |
| `015-schedule-accept-race.mjs`     | `cms_schedule_publication`: the same request twice replays (one schedule); one identity under two keys commits one (`CONFLICT`, never a raw unique violation); a schedule parked after its locks blocks an append which then invalidates the review and cancels the pending schedule (`approval_invalidated`); an append holding the entry row blocks a schedule (`VERSION_MISMATCH`); a schedule and a publish of one review both commit.                                                                                                                                                                                    |
| `016-lineage-append-race.mjs`      | `cms_append_publication_lineage` (the helper itself, one committed session each): two appends from the same head serialize on the lineage advisory lock (the second BLOCKS while the first is parked before its insert, then commits as version 2 naming the first as predecessor, no conflict surfaced); six simultaneous appends commit versions 1..6 exactly with one event each; a publish and an unpublish at once commit as versions 3 and 4 in one serial order.                                                                                                                                                       |

The review runners' fixture is `infra/database-races/review-kit.mjs`: the pgTAP fragments of
`../phase_02_slice_11_rpc_review/` run once in a script that commits, plus `090-race-fixture.sqlinc`.
The preview runner's fixture is `infra/database-races/preview-kit.mjs`: the same fragments plus
`../phase_02_slice_11_rpc_preview/000-world.sqlinc` and `090-race-fixture.sqlinc` (the entries and the committed
Vault history-signing key), and a gate trigger on `cms_preview_tokens` that parks a `s11race-pvgated-<key>-<label>`
session right before its token insert.

The schedule / publication runners' fixture (013-015) is `infra/database-races/publication-kit.mjs`: the same fragments plus
`../phase_02_slice_11_rpc_publication/` (`000-world.sqlinc`, `090-race-fixture.sqlinc`: 34 approved reviews and 26
schedules dated 30 days ahead that a runner makes due with `makeDue`, because a claim is global).
