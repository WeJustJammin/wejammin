## Overview

Shard 03 is the CMS authoring control plane. It owns bounded editorial type definitions, field schemas, content entries, revisions, review/approval, scheduling, code-approved blocks, templates, reusable patterns, previews, editorial taxonomies, locale variants, and related-content curation. It gives authorized staff WordPress-like operational breadth while prohibiting plugins, themes, arbitrary code, and conversion of identity, authority, money, rights, credits, disputes, or entitlements into generic content.

## Features

- **25.01 Content Types & Schema Registry** — immutable type keys, typed field definitions, safe defaults, relation/domain bindings, immutable schema versions, compatibility checks, and explicit migrations.
- **25.02 Content Entries & Editorial Lifecycle** — schema-driven drafts, autosave/presence, immutable revisions, compare/restore, ownership/review, approvals, scheduling, expiry, and archive.
- **25.03 Templates, Blocks & Page Composition** — code-owned approved block registry, named template slots/bindings, reusable patterns, exact preview/diff, and safe atomic publication.
- **25.05 Taxonomies, Localization & Relationships** — editorial vocabularies/terms, governed assignment and merge aliases, locale variants/fallback, and manual-plus-derived related content.

## Acceptance Criteria

- **AC-CMS-01 — Create content type draft:** Given Actor holds the schema designer capability; the proposed type key is unused, never previously retired, and not a reserved canonical concept, and every field kind, relation target, template and capability is selected from an approved protected registry within quota, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) the authorized schema designer submits one atomic initial aggregate containing the immutable key, label, ownership, source/default locale, workflow key/version, optional default-template-version reference, fields, relations, templates, and capability bindings from approved registries, and (6) return a private version-1 draft with validation/impact state; if the flow cannot complete, reserved, retired or colliding keys and off-registry field, relation, template or capability selections return a typed refusal before any mutation and the transaction creates no partial aggregate; existing drafts and history survive, the key is never reused, and a repeated idempotency key replays the same result.
- **AC-CMS-02 — Change field schema:** Given Actor holds the schema designer capability and the target content type version is still an unactivated draft; the field's stable key and UUID already exist for a change or deprecation, new kinds, protected validator key/version and constraints come from the protected registry, and removal is expressed as deprecation rather than deletion, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) add/deprecate/change one field definition; preview affected entries/templates/API projections and classify compatibility, and (6) return a compatible draft; breaking draft requires a migration plan before review; if the flow cannot complete, off-registry kind/validator, free-form pattern/code, key reuse, a change attempted against an already-active version, or a conditional/breaking change without a proven complete non-fabricating transform returns a typed refusal before mutation; the draft keeps its prior definition and a required field over populated entries stays blocked until a valid migration plan exists.
- **AC-CMS-03 — Bind domain record:** Given Actor holds the schema designer capability on a draft type version, and the requested target kind and named projection are both on the domain allowlist with `cardinality`, `min`, `max`, `ordered`, and an explicit `on_unavailable` behavior, where `min` is an integer `0..128`, `max` is a finite non-null integer `1..128`, `min<=max`, `one` requires `max=1` and `min` `0|1`, and `many` uses explicit finite bounds, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) define a read-only typed relation to an allowlisted domain projection; target access/visibility is evaluated at preview/read/publish, and (6) return a binding storing canonical target kind/ID rules, bounds, ordering, and unavailable behavior, never authority; if the flow cannot complete, non-allowlisted target kinds/projections or invalid bounds are refused before mutation; a target that is private, embargoed, deleted, or concealed is omitted or blocks per the relation's `on_unavailable` contract, or resolves to exactly `{status:'unavailable', reason:'unavailable'}` for `placeholder`, at preview, publication and public hydration, never leaking existence or copying stale target fields.
- **AC-CMS-04 — Activate schema version:** Given Candidate version is approved with zero unresolved references, a recorded dry-run report, a valid migration plan for conditional or breaking classes, and proven impacted template/block compatibility; the immutable workflow key/version has resolved its required roles and distinct-human count, and the schema designer cannot activate alone, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) freeze candidate, verify that the recorded dry-run report (produced by CMS-03A-10) and the approved review with its independent approve decisions (produced by CMS-03A-11, CMS-03A-14 and CMS-03A-12) are current, resolve and persist immutable workflow-policy evidence (`key`, `version`, `policyHash`, `requiredDecisionCount`, `requiredCapabilities`) plus `approvalEvidenceHash` server-side, treat the supplied approval IDs as references to those approve decisions and resolve them to distinct humans/capabilities under current assignment authority with the activator's own current MFA verified, collect exactly the policy-required approvals, then atomically mark version active and enqueue migration/projection work, and (6) return prior active remains usable until switch; version cannot mutate; if the flow cannot complete, missing policy-derived evidence, an unresolved reference or a failed compatibility check blocks the switch and returns the candidate to preflight; a partially completed migration resumes from its durable cursor under the same idempotency key, failed rows remain on the old readable schema, and rollback before the switch stops the migration with the prior active version still serving.
- **AC-CMS-05 — Create/edit entry:** Given Actor holds the CMS author capability and is assigned to the target entry, or holds the CMS author capability for a new entry whose requested content type has an active compiled schema version, the entry lifecycle is active with a compiled active schema version, and every autosave carries the changed field paths plus the base revision the draft was loaded from, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) either atomically create the active entry, its attributable first draft revision, initial assignment, and audit/idempotency/outbox effects from server-derived identity under a required idempotency key (BE03b `CMS-03B-10`), or load the caller's assigned or owned entries through the protected entry-list read (BE03b `CMS-03B-13`) and the creatable types and author-safe field definitions through the protected authoring-context read (BE03b `CMS-03B-14`), or load only the caller-authorized editable values, field provenance and explicit schema identity through the protected draft-detail read (BE03b `CMS-03B-11`), then open the schema-driven draft, acquire a renewable presence lease, edit structured fields/blocks/relations, and autosave with expected version, and (6) return the canonical created entry with its first draft revision or a new attributable revision; a refused or replayed create commits no entry or first revision and never duplicates an effect; a concealed or absent draft-detail target returns a policy-safe 404 and a visible-but-unassigned target returns 403 without disclosing hidden values, ownership, or authority; the draft-detail read returns the server-derived `revisionNumber` and `schemaVersionId` and the single durable open conflict and is `no-store` with a strong authenticated `ETag` and no mutation effect; the entry-list and authoring-context reads are bounded, `no-store` and never disclose an entry or schema the caller cannot read; autosave never publishes; if the flow cannot complete, authority revoked mid-edit rejects the commit, preserves the local unsent value, and removes the presence lease and assignment; a moved base revision returns a typed 409 carrying only the conflict identity and versions (the base, theirs and yours safe values are read through the protected conflict-detail read, never carried by the 409; DEC-142); none of these routes trusts caller-supplied owner, acting party, capability, schema, or authority, the authoring-context read never grants schema-registry read, and browser direct table access stays revoked; drafting continues through non-critical dependency failure and nothing is published.
- **AC-CMS-06 — Resolve concurrent edit:** Given A same-field divergence from the same base revision is recorded on an entry the actor may edit, and both competing revisions plus their common base are still readable, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) load the protected three-way conflict detail (BE03b `CMS-03B-12`) for the readable open conflict, whose base, theirs and yours preimages are each schema-typed against their own recorded schema version and which omits any value the caller cannot read, then Different fields merge; same-field/version divergence surfaces both values and requires explicit choice, and (6) return No silent overwrite; resolved revision references both parents; a concealed or absent entry or conflict is a policy-safe 404 and a visible entry without read scope is 403, the conflict-detail read is `no-store` with a strong authenticated `ETag` and no mutation effect, and a resolved or superseded conflict is the same policy-safe 404 as an absent one (the editor treats a 404 after a 409 as "conflict no longer open" and refetches the draft; DEC-139); if the flow cannot complete, No resolution is ever inferred: an unanswered conflict leaves both revisions intact and the draft unresolved, and a choice submitted against a base that moved again returns a typed 409 carrying only the conflict identity and versions and requires a fresh explicit resolution after re-reading the preimages through the conflict-detail read.
- **AC-CMS-07 — Compare/restore revision:** Given Actor may read the entry's revision history and both compared revisions exist with their recorded schema, template and taxonomy versions; a restore additionally requires edit capability plus a registered immutable migration chain manifest composed from the completed schema-migration plan edges (each edge bound to its target version's activation, consecutive, at most 64 edges, with a zero-edge manifest valid for a same-schema restore) whose derived `migrationChainId` the restore must match, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Compare field, block and relation changes across schema-aware versions, reporting only per-side hashes and, for relations, a privacy-safe stable target token that never discloses a target identifier, and refusing with a typed reason above 512 combined changes or when a recorded version is unresolvable rather than returning a truncated success; restore creates a new draft under current compatible schema from the derived chain, revalidating every value including rich-text and object structures, and (6) return History remains append-only; no past revision changes; if the flow cannot complete, A mismatch with the derived chain manifest, a chain with more than 64 edges or an unresolvable path, a missing registered transform, a required field without a literal default or an incompatible template refuses the restore with a typed reason and fabricates nothing rather than activating an obsolete schema; history stays append-only so a refused restore alters no past revision, and revisions the actor cannot read return a typed unavailable without existence leakage.
- **AC-CMS-08 — Submit/review/approve:** Given Revision is in draft state on an entry the submitter may edit and its frozen hash and dependency manifest resolve; each decision requires a reviewer distinct from the author and from the submitter where the workflow says review, every decision requires recent binding MFA and a protected risk class additionally requires two distinct humans and the named specialist capability, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Freeze candidate hash/version; the existing owner assigns eligible reviewers through a bounded, owner-only reviewer assignment (BE03b `CMS-03B-18`, DEC-136) while the submitter, reviewers and owner read the frozen preparation, review detail and reviewer queue through protected reads (BE03b `CMS-03B-15`, `CMS-03B-16`, `CMS-03B-17`); comments/rejections are attributable; high-risk classes require separation, and (6) return Approved candidate remains invalid if content/dependency/authority changes; if the flow cannot complete, missing or stale MFA returns a typed step-up recovery without recording a decision, and Self-approval, a stale frozen hash, a revoked reviewer capability, a missing second reviewer or a changed dependency returns a typed refusal and blocks publish; any later revision or dependency change moves the review to invalidated automatically and a new frozen candidate must be resubmitted.
- **AC-CMS-09 — Schedule publish/expire:** Given Actor holds the CMS publisher capability with recent binding-bound MFA, is not the author of the revision, the target revision is approved with its frozen hash and dependency set intact, and the request supplies a local datetime, IANA timezone, unambiguous resolved UTC instant and tzdb version, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Choose local timezone/instant and optional expiry/archive action; preflight immediately and again at execution, and (6) return Idempotent job transitions exact approved version once; if the flow cannot complete, An ambiguous DST instant requires an explicit earlier or later choice and a nonexistent one is rejected with valid alternatives; preflight failure at execution moves the schedule to blocked with the prior publication intact; a late or repeated run performs the exact-version transition once, records actual time and deviation, and never duplicates a publication.
- **AC-CMS-10 — Register block version:** Given Registration arrives from a signed code release rather than an admin session, the block key and version are code-owned and immutable, and the release supplies an Ed25519 envelope (`keyId`, `issuedAt`, `nonce`, `signature`) over the versioned domain separator, key ID, timestamp, nonce, and SHA-256 of the exact raw body, plus the Zod props schema reference/hash, normalized signed props snapshot, release digest, renderer reference, allowed children/slot rules, data-source permissions, accessibility contract, compatibility range and signed monotonic block `lifecycle` (`supported` → `deprecated` → `withdrawn`), when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) the release worker registers typed props identity/evidence, allowed children/data sources, accessibility contract, renderer, compatibility, and signed monotonic block `lifecycle` (`supported` → `deprecated` → `withdrawn`), and (6) return registration metadata that admins may configure/read only; if the flow cannot complete, an unsigned/mismatched/revoked/out-of-window release, replayed nonce, uploaded script/style/template/expression, dynamic import or unknown renderer/data-source reference is rejected and no version is registered; a withdrawn version leaves existing publications on the last approved compatible renderer and blocks new publishes unless security or takedown requires failing closed immediately, and no browser mutation route exists.
- **AC-CMS-11 — Define template:** Given Actor holds the template designer capability, every referenced block version is registered and currently supported, and the target content types, locale/audience and reserved regions — including the Shard 02 fixed profile spine and provenance components — are declared and left intact, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Compose named slots from approved block versions and bindings; preserve reserved regions and content-type compatibility, and (6) return Versioned template candidate with exact impact set; a candidate becomes active only through the governed, reviewer-gated activation (the designer submits, independent assigned reviewers decide with recent binding MFA, and an atomic compare-and-swap switch activates it and emits `cms.template.activated.v1`; the designer cannot activate alone); if the flow cannot complete, Reordering or removing a reserved provenance or fixed-profile region, exceeding slot depth or count limits, or referencing an unregistered, retired or incompatible block version is rejected by validation before review or publish, leaving the prior active template version unchanged.
- **AC-CMS-12 — Use reusable pattern:** Given Actor may edit the target entry revision or template draft, the referenced pattern version is immutable and readable, and the resulting block tree stays acyclic within the protected depth and count limits, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Insert linked pattern, accept reviewed update diff, or detach to local copy, and (6) return Pattern never silently overwrites local content; recursive graph rejected; a persisted pattern version is created by the template designer, selected through an author-facing selector of active compatible versions, and activated through the same governed review (`cms.pattern.activated.v1`); a linked update waits as a pending three-way diff until explicitly accepted or detached; if the flow cannot complete, A recursive or cyclic pattern graph and any depth or count overrun are rejected before save; a linked update colliding with local overrides presents a three-way diff and waits for explicit accept or detach, and an unanswered update leaves the instance on its current version with nothing overwritten.
- **AC-CMS-13 — Preview/diff/publish:** Given Preview requires a capability on the target entry and mints a token bound to user, acting context, revision, the full version set, audience/locale/route, expiry and nonce, rechecked on every open; publish additionally requires the CMS publisher capability, an approved revision whose frozen hash and dependency set still match, recent binding-bound MFA, a publisher who is not the revision's author, and a preflight rerun across the registry of preflight categories against current revocation state, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Create short audience-bound preview over exact entry/schema/template/taxonomy/settings versions; compare to active projection; publish chosen set, and (6) return Canonical publication and outbox commit atomically; public convergence is versioned; if the flow cannot complete, A forwarded, expired or revoked preview token is denied on recheck and leaves no public cache or search trace; a publish racing a newer schema, template or taxonomy version returns a typed expected-version-set conflict and sends the candidate back to preflight with no partial write because publication and outbox commit together; control-plane unavailability keeps the validated last-known-good unless privacy, security or takedown requires immediate fail-closed removal.
- **AC-CMS-14 — Govern taxonomy term:** Given Actor holds the taxonomy curator capability for that specific editorial vocabulary, the term key is stable and the proposed hierarchy stays acyclic, canonical-taxonomy overlap has been checked, and a merge names a survivor whose counterpart is not already merged, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Curator proposes/create/rename/alias/deprecate/merge term after overlap and impact checks, and (6) return Stable term ID/key survives aliases/merge redirects; assignments converge; the vocabulary is a versioned rule set (shape, type/field allowlists, declared canonical overlap domains) activated through the governed review; if the flow cannot complete, Overlap with the canonical taxonomy is rejected with a pointer to the canonical ID to reference instead; an unassigned vocabulary, a cyclic parent or reactivating a merged term is refused; a merge racing live assignments locks terms and aliases, preserves the retired ID as a permanent redirect, and converges assignments exactly once.
- **AC-CMS-15 — Author locale variant:** Given Actor may edit the entry in the requested BCP 47 target locale, a source-locale revision exists for the fields being translated, only schema-localizable fields are in scope, and the ordered fallback chain is the one the active content-type version declares for the target locale (the request may carry it only as an equality expectation), when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Translate allowed fields, track `untranslated|draft|review|approved|stale`, and preview explicit fallback chain, and (6) return Legal/safety/no-fallback fields block locale publish when absent/stale, a `no_fallback` field resolving only from its own locale variant and a stale fallback-permitted field keeping its last approved translation; if the flow cannot complete, A source-locale change marks the dependent translations stale and explicit revalidation is required to return to approved; a missing or stale `no_fallback` legal, safety or jurisdictional field blocks that locale's publication with a typed refusal and never borrows another jurisdiction's text; unchanged fields keep their approved state.
- **AC-CMS-16 — Curate related content:** Given Actor may edit the source entry, every pinned or excluded target is an existing entry the acting context is authorized to reference, and derived candidates come only from explainable bounded deterministic rules over currently authorized projections, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Pin/exclude eligible targets and review explainable derived candidates; target authorization and publication state recheck, and (6) return Manual pins lead, exclusions win, stale/unavailable targets disappear safely; a pin must be an existing, active, same-owner entry the actor can read, and derived candidates come only from the code-owned shared-terms and same-type-recent rules; if the flow cannot complete, A pin to an unauthorized or nonexistent target is refused without leaking existence; a target that becomes unpublished or unavailable drops out of the public relation while its editorial explanation and history are retained, and the slot refills only from eligible candidates because a recommendation never grants access.

### Global Interaction Rules

- Every definition/value/change is typed, scoped, versioned, attributable, previewable, auditable, and reversible by a new version—not an in-place production edit.
- CMS-03A-01 validates and persists the complete initial type aggregate in one idempotent transaction; no field, relation, template, capability, artifact, or workflow child is committed or exposed without its parent version.
- Product-operable variables use governed definitions/settings; security, authorization, legal floors, money/ledger, state-machine, migration, evidence, and secret invariants remain code/rule-pack contracts.
- Drafting may continue during non-critical dependency failure; activation/publish fails closed when validation, authority, privacy, accessibility, migration, or required dependency evidence is unavailable.
- Protected registry list/detail reads are capability-scoped and `no-store`; public routes consume only Shard 04 publication projections and never control-plane rows.
- Entry bootstrap is a human form that requires an `Idempotency-Key` and no update-only `If-Match`; the draft-detail read is a protected read-only `GET` with no mutation effect, no body, no idempotency key, and no precondition header; the entry-list, authoring-context and conflict-detail reads are likewise safe, bounded, `no-store` reads that never disclose an entry, value, schema or ownership identifier the caller cannot read.

### Schema Activation Producers (DEC-108)

CMS-04 is a reachable protected command chain, not acceptance of manually
inserted approved rows: CMS-03A-09 creates a successor draft, CMS-03A-10 starts
an actual dry-run attempt/job whose completed report is immutable,
CMS-03A-11 freezes a passed candidate
for review, CMS-03A-14 assigns or revokes narrowly bounded reviewers,
CMS-03A-12 records independent decisions, CMS-03A-13 reads the authorized review,
and CMS-03A-04 activates only after current readiness evidence passes. Existing
operation IDs remain stable. Every mutation retains BE00 CAS, idempotency,
origin/CSRF, current authority, transaction, audit and outbox gates.

Schema reviews belong to CMS, not the settings-owned CFG ledger. The private
`cms_schema_reviews`, `cms_schema_review_decisions` and
`cms_schema_review_assignments` tables have common model envelopes, ENABLE/FORCE
RLS and no direct browser or service-role table grants; only named private
commands can access them. Reviews freeze candidate/version/definition/artifact,
compiler/dependency/dry-run identity, submitter and stable context evidence,
workflow key/version/hash/risk/count/capabilities and approval digest. Frozen
fields are immutable; states are `open|approved|rejected|invalidated`.

`cms.schema_review` grants only read/decide on one assigned frozen review.
The existing owner alone has `cms.schema_review.assign`; current effective owner
authority means the immutable owner initialization receipt identity and the
owner's currently valid `cms.schema_designer` grant. Assignments reference an
eligible existing human, expire within seven days and no later than the
grantor's authority end (the end of that grant's valid-through day; the receipt
grant end bounds only the grants created at owner initialization, and the owner
renews its own authority through the owner CMS capability grant commands
below), grant no owner acting context and confer no admin, design,
entry-edit or publishing authority. Unknown/ineligible humans, submitters,
cross-owner targets, broad scopes and delegation are refused. Authority is
effective only while `starts_at<=now<ends_at`, with current binding and MFA
independently verified; no expiry sweep is required for enforcement.

Each human can record one append-only decision per review and the submitter
never counts. Ordinary policy requires one independent eligible reviewer;
protected policy requires at least two, with exact count `1..8` resolved from
the code-owned workflow registry. Decision commit records recent binding-bound
MFA. Activation rechecks live assignments/capabilities, frozen policy/evidence
and the activator's current MFA; a decision does not expire solely because ten
minutes elapsed. Candidate, policy, compiler, dependency or reviewer-authority
drift invalidates the review. Rejection returns the candidate to an editable
draft through an audited transition; resubmission freezes new evidence.

Review binding hashes use a versioned stable internal projection of verified
actor/person/party/binding identity, excluding request/correlation IDs and
transport timestamps. Versioned canonical SHA-256 approval evidence binds the
exact sorted decision set and frozen review composition. Raw matching IDs stay
server-side and out of browser props, public evidence resources and logs;
confirmation receives only a verified safe context label and expiring MFA
metadata. Authorized public content/review references and lowercase 64-hex
evidence digests are not private identity disclosures.

Only the minimum real entry-create/draft-read authority, actual source scanner
and code-owned transform adapter, immutable template-draft creation
`POST /api/v1/cms/templates/versions` and named service-only compatibility RPC
`platform_api.cms_resolve_template_compatibility` are prerequisites within
Slice 09. The resolver checks exact type/version/template references under
verified actor/owner scope, conceals wrong-scope targets and rejects incompatible
or withdrawn definitions. It is a nonmutating read/preflight. Public template
activation remains a separate Slice 12 governed transition, not an AC169
prerequisite. Other Slice 10/12 outcomes remain gated and unaccepted.

### Workflow Policy Registry and Owner CMS Capability Grants (DEC-109, DEC-110, DEC-119)

Review policy comes from one code-owned, versioned registry of members
`{ key, version, riskClass, requiredDecisionCount, requiredCapabilities }`,
seeded as immutable rows by a forward-only migration and bound one per content
type version through `workflow_key`/`workflow_version`; a policy changes only by
code plus a forward migration and a caller-supplied policy is never authority.
Every member is version 1. The ordinary members `editorial`,
`editorial.default`, `cms.content.workflow` and `cms.standard` each require one
independent `cms.reviewer` decision. The protected members
`cms.disclosure.policy`, `cms.disclosure.legal`, `cms.disclosure.security` and
`cms.disclosure.financial` each require two distinct humans, at least one of
whom holds the class specialist capability `cms.reviewer.policy`,
`cms.reviewer.legal`, `cms.reviewer.security` or `cms.reviewer.financial`.
`requiredCapabilities` is an ordered list of reviewer slots: the first is the
base reviewer slot every counted decision satisfies and each further entry is a
specialist slot at least one counted approving human must hold. `policyHash` is
the SHA-256 of the RFC 8785/JCS canonical member. A schema review derives its
policy from the candidate version's own bound member (an ordinary member needs
one assigned `cms.schema_review` decision, a protected member two with the
specialist held through a grant, never through an assignment alone); an
editorial review derives its policy from the entry's content-type version. A
successor never lowers either requirement: a successor's schema review and the
editorial policy its version carries use the strictest of the source version's
member and the candidate's own member, so a protected-to-ordinary key change
still needs the protected count and the specialist slot. A
review is approved only when the distinct qualifying approvers equal the
required count and every specialist slot is held by one of them, and an approve
decision that would leave a specialist slot unsatisfiable is refused.

The existing owner alone provisions CMS capabilities, so reviewers, authors,
editors, template designers, taxonomy curators, publishers, navigation editors,
media contributors, media curators and specialist reviewers are reachable without direct grant-row writes. Grant, renew and revoke
are protected commands, and a protected list serves the console. The owner is
derived from the immutable owner initialization receipt identity with a live
binding and recent MFA and does not need a currently valid grant, so an owner
whose seven-day bootstrap grants have lapsed renews its own
`cms.schema_designer` and `cms.schema_registry.read` authority without
re-bootstrap. A grant names one capability from the closed grantable CMS
registry and one existing human with a confirmed membership in the owner's
organization; it ends at the end of a UTC date no later than the current UTC
date plus 89 days, so a term spans at most 90 UTC days (DEC-120); assignments
under DEC-108 stay at most seven days. Renewal restarts a fresh finite term of
at most 90 UTC days, requires step-up, may be repeated, and revocation is immediate. A grant creates
no identity or membership and confers no admin, grant, delegation or purpose
authority; `cms.schema_review` and `cms.delivery_review` (assignment-only),
`cms.schema_review.assign` and `cms.delivery_review.assign` (owner-only),
`admin.*` and non-CMS capabilities are never grantable. The owner may grant
itself any grantable capability: the owner is the only human in the
organization today, so a grant-time self-limit would deadlock authoring, and
separation of duties is enforced at decision time (the submitter is never the
reviewer, each counted decision is a distinct human, and each specialist slot
is held by a counted approver), not at grant time. A subject outside the owner's organization is
indistinguishable from an absent one. Every grant mutation retains BE00 CAS,
idempotency, origin/CSRF, current authority, transaction, audit and outbox
gates. The integrated acceptance path provisions its test humans only through
these commands.

### Templates, Blocks, Taxonomy, and Locale

The block registry digest is the SHA-256 lowercase hexadecimal digest of the RFC 8785/JCS canonical JSON for the sorted reachable block-version tuples `{blockKey,blockVersion,releaseDigest,propsSchemaHash,rendererRef,lifecycle}`, sorted by `blockKey` UTF-8 and then numeric `blockVersion`. The server resolves and recomputes it at template/pattern create and activate and publication preflight; a client-supplied digest is expected evidence only. CMS-03A-05 uses an Ed25519 signed release envelope with protected key validity/revocation, a five-minute clock-skew limit, a nonce replay store retained at least ten minutes, and rotation overlap.

Relation bounds are finite and non-null: `min` is integer `0..128`, `max` is integer `1..128`, `min<=max`; `one` requires `min` `0|1` and `max=1`, and `many` always has explicit bounds. For `on_unavailable=placeholder`, every private, deleted, embargoed, or concealed target resolves to exactly `{status:'unavailable', reason:'unavailable'}` with no target ID/type/key/title/data or existence distinction.

### Common Model Envelope and Exceptions

Every persisted Shard 03 model uses the explicit envelope `id: uuid`, `owner_id:
uuid`, `state: closed enum`, `version: bigint`, `created_at: timestamptz`, and
`updated_at: timestamptz`. `owner_id` identifies the owning party or parent
aggregate and never grants authority; code-owned rows identify the release
principal or release record. Immutable definitions, revisions, decisions,
labels, links, and artifacts set `updated_at = created_at` and reject updates;
new versions or append-only rows carry later changes.

| Model group                                                                                                                  | Envelope interpretation                                                                                                                                                                           | Explicit exception or additional rule                                                                                                                                                                                                                                                                                                   |
| ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ContentType`, `ContentTypeVersion`, `FieldDefinitionVersion`, `RelationDefinition`, `SchemaArtifact`, `SchemaMigrationPlan` | The owner is the type/definition aggregate; `state` is lifecycle/workflow state and `version` is the immutable definition or operation version.                                                   | `ContentType.lifecycle` is separately `active\|retired`; `ContentTypeVersion` also has `source_locale`, `default_locale`, and optional `default_template_version_id`; `SchemaArtifact` is immutable and content-addressed.                                                                                                              |
| `ContentEntry`, `EntryRevision`, `EntryFieldValue`, `EntryRelation`, `EditPresence`                                          | The owner is the entry aggregate; revision/link versions are monotonic and scoped to the entry.                                                                                                   | `EditPresence.state` is `active\|expired\|revoked`, is advisory, and its renewal updates `updated_at`; it is never evidence of authorization. The bootstrap path creates the `ContentEntry` and its first `EntryRevision` in one transaction, so no `EntryRevision` exists without its entry and concealed entries are never reachable. |
| `EditorialReview`, `EditorialDecision`, `PublicationSchedule`, `PublicationVersion`                                          | The owner is the entry/review aggregate; state transitions are closed and auditable.                                                                                                              | `EditorialDecision` and `PublicationVersion` are append-only evidence; publication rows retain prior versions and `updated_at = created_at`. `EditorialReviewAssignment` is a mutable CAS envelope (`active` to `revoked`); `EntryRevision` keeps its stored state immutable and its workflow state is derived from review, schedule and publication evidence; `PublicationVersion` rows form an append-only lineage with a derived `superseded`. |
| `BlockDefinitionVersion`, `TemplateVersion`, `PatternVersion`, `CompositionInstance`                                         | The owner is the release or composition aggregate; versioned renderer/binding state is immutable after approval.                                                                                  | `BlockDefinitionVersion.owner_id` points to the signed release record; props schema identity is `props_schema_ref + props_schema_hash`, while the snapshot is derived evidence bound to `release_digest`.                                                                                                                               |
| `TaxonomyVersion`, `TaxonomyTerm`, `TermLabel`, `TermAssignment`, `LocaleVariant`, `RelatedContentRule`                      | The owner is the vocabulary or entry aggregate; labels, assignments, locale states, and curation rules are versioned/append-only.                                                                 | `TermLabel` and `TermAssignment` use parent aggregate ownership; `LocaleVariant` stores both source locale/revision and target locale; no fallback or assignment grants access.                                                                                                                                                         |
| `CapabilityGrant`, `CapabilityGrantEvent`, `WorkflowPolicy`                                                                  | The owner is the organization (grant and event) or the seeding release record (policy); `state` is `active\|revoked` for the grant aggregate, `recorded` for events and `seeded` for policy rows. | The grant aggregate is the only mutable row and changes by version CAS; events and policy rows are immutable with `updated_at = created_at`; the API's derived `lapsed` is never a stored state.                                                                                                                                        |

Child rows must carry their parent `owner_id` even when their foreign key is
more specific. A missing envelope field is therefore an explicit schema error,
not an implicit exception.

The only lifecycle-named envelope states are `ContentType.lifecycle`,
`ContentEntry.lifecycle`, `BlockDefinitionVersion.lifecycle`, and
`TaxonomyTerm.lifecycle`; each is the
physical closed `state` for that model and is not duplicated as a second
mutable state. All other persisted models expose an explicit closed `state`
column. Immutable rows set `updated_at=created_at` and reject updates; advisory
`EditPresence` renewal is the sole documented timestamp-refresh exception.

## Access Control

| Capability              | Allowed                                                                                     | Explicit denial                                                       |
| ----------------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| CMS author              | Create new entries and edit assigned entry drafts with eligible relations/media references. | Publish, schema/template/taxonomy changes, private domain access.     |
| CMS editor              | Review/edit eligible content and return/reject drafts.                                      | Self-approve protected risk class, change platform contracts.         |
| CMS publisher           | Schedule/publish approved validated revisions after recent binding-bound MFA. | Publish stale/unapproved hash, bypass blockers, or publish a revision they authored. |
| Schema designer         | Draft type/field/relation/migration definitions.                                            | Activate alone, reserve canonical concepts, arbitrary SQL/code.       |

| Taxonomy curator        | Govern assigned editorial vocabulary/terms and impact; create vocabulary versions, submit them for governed review and activate an approved version. | Edit canonical domain taxonomy or unrelated vocabulary, activate without independent reviewer approval. |
| Legal/security reviewer | Review assigned protected content/rule metadata with MFA.                                   | General tenant access or ordinary publishing authority by role alone. |
| Assigned reviewer       | Read and decide on one assigned frozen editorial or governed (template, pattern, taxonomy) review while holding the standing `cms.reviewer` grant (and a specialist capability for a specialist slot). | Decide a review they authored or submitted, edit, publish, assign, or exceed the assignment window. |

Schema-review approval is a separate bounded capability from schema design:
assigned `cms.schema_review` humans may read/decide only the exact frozen review,
while owner-only `cms.schema_review.assign` may create/revoke that assignment
with recent binding MFA. Neither capability grants admin/design/publish access.

Platform administration is a named bounded capability, not a persona or universal tenant. Every operation rechecks human, acting context, capability, assignment, risk, target, version, and RLS/RPC at commit.

## Edge Cases

| Case                                                                                       | Required result                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Type/field key collides with reserved/retired meaning                                      | Reject activation; draft/history survive; key never reused.                                                                                                                                                                                                                                                                        |
| Required field added to populated entries                                                  | Breaking migration required unless safe non-fabricating default and complete impact proof exist.                                                                                                                                                                                                                                   |
| Relation target becomes private/embargoed/deleted                                          | Viewer read rechecks; omit/block per relation contract, or return exactly `{status:'unavailable', reason:'unavailable'}` for placeholder; never leak existence, target identifiers, or copy stale fields.                                                                                                                          |
| Migration partially succeeds                                                               | Resume from durable cursor/idempotency; old active version remains readable until switch.                                                                                                                                                                                                                                          |
| Two editors change same field                                                              | Preserve both revisions and require explicit resolution; no silent last-write-wins.                                                                                                                                                                                                                                                |
| Authority revoked during autosave/review                                                   | Reject commit, preserve local unsent value, remove active presence/assignment.                                                                                                                                                                                                                                                     |
| Entry create replayed or refused                                                           | A repeated create idempotency key replays the same entry and first revision without a second effect; a refused create commits neither the entry nor its first draft revision.                                                                                                                                                      |
| Draft-detail target concealed or unassigned                                                | Return 404 for an absent or concealed entry and 403 for a visible entry the actor may not read; never disclose hidden values, ownership, or authority, and serve `no-store` with no mutation effect; the conflict-detail read applies the same concealment and never serializes an ownership or resolver identifier. |
| Conflict detail requested after resolution or supersession | The same policy-safe 404 as an absent conflict (DEC-139); no metadata and no preimages are returned, and the editor refetches the draft. |
| Draft advances past an open conflict | A non-conflicting append or a restore supersedes every open conflict of the entry in the same transaction, so a conflict never stays open against a draft that moved on; resolving a conflict that is no longer open is a typed 409 (invalid transition) that changes nothing, while reading it is the policy-safe 404 (DEC-139). |
| Entry list collection changes between pages | The signed cursor is bound to the collection epoch of its position. If an unseen entry moved ahead of the position, an entry was created or left ahead of it, or the caller's collection emptied, the next page is a typed 409 with restart-from-the-first-page recovery, never a silent skip or repeat; an entry updated behind the position is listed in its new place. |
| Writer races authority revocation or schema activation | A revocation committed before the writer's lock wins (the write is refused and no row is written); an activation briefly serializes the organization's authoring writes and a writer that waited targets the new active version or is refused with a typed error; a deadlock outside the global lock order is a typed retryable 409 (retry with the same idempotency key). |
| Entry creator holds only the editor capability | The creator's initial assignment carries the capability they proved (`cms.editor`), so they can append to and read the entry they just created; a creator with neither capability creates nothing. |
| Entry-list or authoring-context scope | The list returns only entries assigned to or owned by the caller and the authoring-context read returns only creatable types or one author-safe field projection; neither discloses an entry, schema or ownership identifier outside the caller's scope, and neither grants schema-registry read. |
| Comparison exceeds 512 combined changes, or a recorded version is unresolvable | The comparison is refused with a typed reason (`comparison_too_large` or the non-disclosing `comparison_unavailable`), never a truncated success; relation changes expose only the keyed stable token and never the target identifier. |
| Restore chain identity does not match, exceeds 64 edges, or is unresolvable | The restore is refused with a typed mismatch/unavailable reason and changes nothing; a same-schema restore uses the zero-edge manifest and a missing transform, a required field without a literal default or an incompatible template refuses with nothing fabricated. |
| Rich-text value is non-canonical, unsafe-scheme or executable | Refused with a typed reason rather than canonicalized server-side or rendered as raw HTML; the stored value is always the canonical `rich_text.v1` AST. |
| Object field lacks a typed structure or a value does not satisfy it | Refused with a typed reason; an `object` field and value are always validated against the frozen depth-1 `properties[]` structure and are never stored untyped. |
| Schema review assignment expires or is revoked mid-review                                  | Authority is effective only while `starts_at<=now<ends_at` with current binding; an expired or revoked reviewer's decision cannot be recorded and activation rechecks live assignment/capability, so a decision from a no-longer-authorized reviewer does not count; the review stays frozen and other assignments are unaffected. |
| Submitter or duplicate schema review decision                                              | The submitter never counts; a second decision by the same human on the same review is refused as append-only and neither row is changed or deleted.                                                                                                                                                                                |
| Concurrent schema review decisions race the required count                                 | Concurrent decisions race on the review's exact version; the loser receives a typed 409 for a stale review version and refetches, and the review is approved only when the frozen policy's required count of independent eligible approve decisions exists, with an approved review's count equal to the policy count exactly.     |
| Schema candidate, policy, compiler, dependency or reviewer authority drifts after approval | The review is invalidated, activation is refused with a typed error and the candidate returns to preflight; resubmission freezes new evidence and approvals are never reused.                                                                                                                                                      |
| Schema review is rejected                                                                  | The candidate returns to an editable draft through an audited transition; prior review and decision rows remain immutable, and resubmission freezes new evidence.                                                                                                                                                                  |
| Schema candidate edited while in review | A definition edit is admitted only to atomically invalidate the open review and its decisions and return the candidate to draft; an approved candidate stays frozen and the edit is refused with a conflict. |
| Source data changes after the review freeze | The scan evidence no longer matches the live source. The refusing call (activation switch, begin-verification or complete) returns a typed conflict (detail `MIGRATION_SOURCE_DRIFT`) and changes nothing. Recovery is a new dry run, which atomically invalidates the open or approved review, returns the candidate to draft and starts the new attempt; the verify verdict for drift invalidates eagerly. Resubmission freezes new evidence. |
| Locale-only or other field-neutral breaking change over a populated type | The plan has no changed or retired field: every row is carried unchanged, the scan seals clean and the change completes. A breaking locale-configuration change scans the affected locale variant rows as well as entry revisions, so the plan counts reflect them. |
| Owner CMS grants lapse                                                                     | The owner renews through the owner grant commands, which need only the receipt identity, a live binding and recent MFA and not a currently valid grant; no party is re-bootstrapped.                                                                                                                                               |
| Grant target is absent, banned, unclaimed or outside the owner's organization              | Indistinguishable refusal; no identity, membership or grant is created.                                                                                                                                                                                                                                                            |
| Owner targets itself for a grantable CMS capability | Accepted: the owner may self-grant any grantable CMS capability. Separation of duties is enforced at decision time, never at grant time: the same human can never supply a counted approval for a review they submitted. |
| Specialist capability expires or is revoked after approval                                 | The counted approver stops qualifying, the review is invalidated as reviewer-authority drift, activation is refused and resubmission freezes new evidence.                                                                                                                                                                         |
| Protected review has too few decisions left for its specialist slot                        | An approve decision by a human who leaves the specialist slot unsatisfiable is refused; a reject decision is always accepted.                                                                                                                                                                                                      |
| Two grant commands race on one grant                                                       | Commands serialize on the grant aggregate version; the loser receives a typed 409 and refetches.                                                                                                                                                                                                                                   |
| Draft changes after approval                                                               | Approval invalidates automatically because hash/dependency set differs.                                                                                                                                                                                                                                                            |
| Revision superseded by a newer revision | The live review of the older revision is invalidated and its pending schedules are cancelled in the same transaction; resubmission freezes new evidence. |
| Reviewer assignment expires or is revoked mid-review | An expired assignment cannot record a decision but a decision already recorded stands; a revoked assignment removes an open review's counted decision from the qualifying count; the review stays frozen and other assignments are unaffected. |
| Owner assigns the submitter or revision author | Refused with the same uniform ineligible refusal as an unknown human; nothing is created. |
| Counted approver's standing reviewer capability expires or is revoked after approval | The review is invalidated as reviewer-authority drift; scheduling and publication are refused and resubmission freezes new evidence. |
| Publisher is the author of the revision | Refused as a separation-of-duties violation; a second human holding the publisher capability must schedule or publish. |
| A preflight category's owning domain is not built | The category passes only when the revision holds no reference of that kind; otherwise it fails closed with a typed unbuilt-reference refusal until the owning slice registers its provider (D19). |
| Accessibility checker finds a blocking structural issue | Review submission, schedule acceptance and execution, and publication refuse with the typed preflight refusal; a schedule blocks and the prior publication stays intact. |
| Schedule fire time passes the publisher's grant end | Refused at acceptance; a grant revoked or ended before the fire instant blocks the execution with the prior publication intact. |
| Scheduler runs twice/late                                                                  | Idempotent exact-version transition; record actual time/deviation; no duplicate publication.                                                                                                                                                                                                                                       |
| DST time is ambiguous/nonexistent                                                          | Require explicit earlier/later valid instant or reject nonexistent time with alternatives.                                                                                                                                                                                                                                         |
| Block version withdrawn                                                                    | Existing publication uses last approved compatible renderer unless security/takedown requires fail closed; new publish blocked.                                                                                                                                                                                                    |
| Template attempts reserved provenance/profile reorder                                      | Validation rejects before review/publish.                                                                                                                                                                                                                                                                                          |
| Linked pattern updates with local overrides                                                | Show a pending three-way diff on the instance (which keeps its pinned version); require an explicit choice per colliding path and accept or detach; never overwrite silently; bulk acceptance only when no instance collides. |
| Preview token forwarded/revoked                                                            | Audience/capability recheck denies; no public cache/search trace.                                                                                                                                                                                                                                                                  |
| Publish races newer schema/template/taxonomy                                               | Expected version-set conflict; candidate returns to preflight.                                                                                                                                                                                                                                                                     |
| Taxonomy term merge races assignment                                                       | Lock terms/aliases; preserve old ID redirect; assignment converges once.                                                                                                                                                                                                                                                           |
| Canonical taxonomy overlap                                                                 | Reject editorial vocabulary/term; reference canonical ID instead.                                                                                                                                                                                                                                                                  |
| Vocabulary declares a canonical domain that has no provider | The vocabulary version cannot activate and a term action refuses with a typed canonical-source-unavailable refusal; a vocabulary declaring no domain is never checked and keeps working. |
| Template, pattern or taxonomy version activation lacks approval | Activation refuses; the designer or curator cannot activate alone, an invalidated review returns the version to draft, and a scheduled activation that fails at fire time blocks with the prior active version intact. |
| Related pin to an unauthorized, inactive, other-owner or absent entry | One uniform refusal without existence leakage; exclusions win; derived candidates are drawn only from published, authorized targets. |
| `no_fallback` field value is missing or stale in the target locale | The locale's publication is blocked and the value is never borrowed from the default or another locale; a stale fallback-permitted field keeps serving its last approved translation and never blocks. |
| Restore meets composition instances or term assignments | Instances are re-pinned to the current registry (a withdrawn block, an inactive pattern or an absent slot refuses) and assignments to merged terms re-point to the survivor; an unknown term refuses and nothing is fabricated. |
| Source locale changes                                                                      | Mark dependent translations stale; no-fallback fields block locale publication.                                                                                                                                                                                                                                                    |
| Locale set or fallback chain must change | Only a successor content-type version may change `supported_locales` or `fallback_chains`; it goes through dry run, schema review and activation like any schema change, an active version is never edited in place, and removing a locale or reordering a retained chain is a breaking change. |
| Variant request names a fallback chain that differs from the active version's | Refused as a conflict that returns the active chain; nothing is written and the actor refetches. |
| Related target becomes unavailable                                                         | Remove from public relation, retain editorial explanation/history, refill only from eligible candidates.                                                                                                                                                                                                                           |
| Control plane unavailable                                                                  | Public delivery keeps validated last-known-good unless privacy/security/takedown requires immediate fail-closed removal.                                                                                                                                                                                                           |
