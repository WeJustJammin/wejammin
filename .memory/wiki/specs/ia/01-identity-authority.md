## Overview

Shard 01 owns canonical people, aliases, organizations, memberships, representations, mandates, band governance, external party identifiers, and legacy-party administration. It answers four separate questions: who authenticated, which party they are acting as, what current relationship authorizes the act, and how the resulting fact remains attributable over time. Supabase Auth proves only the first question; PostgreSQL records and guarded commands answer the rest.

## Features

- **01.01 Person Identity & Roles** — one human party with simultaneous role facets; first-class aliases; explicit per-view acting context; structurally separate legal and public identity.
- **01.02 Organizations & Entity Model** — thin party spine, typed capability sets, progressive attributes, weak creation, duplicate signals, multi-type support, and non-destructive lifecycle.
- **01.03 Membership, Representation & Mandate** — time-bounded consented relationships, provenance-labelled historical assertions, scoped delegated authority, and deterministic revocation.
- **01.04 Band & Ensemble Governance** — versioned decision terms, name ownership, treasury authority, dissolution, and successor/fork behavior without deleting work.
- **01.09 Party Identifier Resolution** — namespace/capacity-aware external identifiers, verification/collision states, and fail-safe downstream routing.
- **01.10 Estates, Deceased Users & Legacy Accounts** — successor nomination, verified memorialisation, estate representation, and permanent provenance without deceased-user impersonation.

## Acceptance Criteria

- **AC-IDA-01 — Create person record:** Given A Supabase Auth user is verified and no active person party is already bound to that Auth UUID; the command carries a client idempotency key and creates its own self acting context, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Idempotently create one PostgreSQL person party for the verified Supabase user; matching email/name/provider text never merges people, and (6) return User owns a self acting context; zero facets is valid; if the flow cannot complete, A repeated idempotency key returns the original person rather than a second party, and matching email, name or provider text never auto-merges — control of both accounts must be proven through the Shard 00 merge flow; validation or authority failure returns a typed refusal before any mutation.
- **AC-IDA-02 — Add/remove role facet:** Given The acting human is the subject person, the facet code exists in the current versioned platform registry, the command names exactly one facet, and a removal supplies the expected person version for a facet currently `active`, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Change one facet per command. Add is self-asserted; removal atomically checks the facet's closed live-obligation set and never deletes history, and (6) return Version increments; affected navigation refreshes from canonical capability projection; if the flow cannot complete, A facet with live obligations returns a conflict carrying that facet's closed obligation codes — `seller` listing, order, return or checkout in flight; `teacher` future lesson or running cohort; `producer` open owned project or outstanding contributor invite; `engineer` or `tech` accepted-undelivered service; `performer` future confirmed booking; `writer` issued-unsigned split — and history is never deleted; a concurrent change resolves as a single-facet compare-and-swap so the loser receives a typed version conflict with no set replacement or lost update; a petition for an unregistered facet enters the curation queue and never creates a live value.
- **AC-IDA-03 — Create/retire/transfer alias:** Given The acting human owns the alias through its current open ownership period, creation additionally requires only an active person, the proposed handle is unique after Unicode confusable normalization, and a transfer additionally requires both people to act inside the 7-day offer window; creations are capped at 5 per person per rolling 30 days and handle changes at 2 per alias per rolling 12 months, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Create a single-owner alias with unique confusable-normalized handle and disclosed implied `performer` facet; retirement preserves history; transfer requires both people within 7 days, and (6) return Dated ownership period and permanent handle redirect are committed; if the flow cannot complete, A normalized handle collision is rejected while the display name remains allowed, and no handle is ever reissued; a stale transfer acceptance is rejected, the ownership period is unchanged and the offer may be reissued; exceeding a quota adds friction or review and never transfers ownership or reissues a handle; retirement preserves history and a retired alias never reactivates under a new party.
- **AC-IDA-04 — Switch acting context:** Given The target context is one the current human holds right now — self, an owned alias, an active accepted membership or an active representation — and the switch is a deliberate per-tab and per-device action; a deep link may preselect a context but never satisfies this precondition, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Show self, aliases, active memberships, and representations derived from current records. Switch is one deliberate tap, per tab/device, never triggered by a deep link, and (6) return Persistent text+avatar indicator updates; submit revalidates authority; if the flow cannot complete, A revoked or expired context may still display briefly but fails closed at submit and switches to self with an explanation; an organization or representation context reverts to self after 12 hours of inactivity, and the first attested or monetary action after a session gap requires reconfirmation; a deep link naming another context never switches or executes without a deliberate choice.
- **AC-IDA-05 — Disclose legal identity:** Given An eligible transaction exists, the recipient and purpose are on the current disclosure allowlist, the acting human has completed a recent step-up, the requested field set is the minimum projection for that purpose, and the subject holds a legal identity record whose effective period covers the disclosure, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Require an eligible transaction, explicit audience/purpose, recent step-up, and minimum field projection, and (6) return Disclosure event records recipient, purpose, fields, version, and time; if the flow cannot complete, A missing step-up, ineligible transaction, unlisted purpose or over-broad field set refuses before any disclosure and writes no disclosure event; protected fields are never browser-cached, an alias context can never disclose legal identity, and the counsel-gated privacy hard gate has no role override.
- **AC-IDA-06 — Create organization:** Given The acting human is authenticated and has chosen exactly one creation mode — self-member, shadow or custodial, or external-reference — and any declared types exist in the versioned organization-type registry; more than 3 organizations in 24 hours or more than 10 in a lifetime additionally requires passing friction review, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Choose self-member, shadow/custodial, or external-reference mode; run bounded type-aware duplicate detection before commit without blocking creation, and (6) return One canonical party is created with ownership and lifecycle independent; if the flow cannot complete, Duplicate detection is bounded at a hard 2 seconds, so a timeout commits creation and continues detection asynchronously — the created party is kept and a merge or claim offer opens later, never a silent combination; friction review adds friction but is never a permanent denial by count alone; a type outside the registry is refused before commit.
- **AC-IDA-07 — Add/remove organization type:** Given The actor holds a current owner or admin grant for the organization, the command names exactly one type from the protected registry, an add requires no active assignment for that type while a removal requires one, and the expected organization version is supplied, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Owner/admin adds one type at a time; type-specific fields remain progressive and undiscoverable until their owning-domain gates pass, and (6) return Party identity/history remain unchanged; removed surfaces disappear, not records; if the flow cannot complete, A version conflict returns a typed refusal with no lost update; removing the last type leaves a typeless collective rather than deleting the party, and history and links persist; type-specific fields stay undiscoverable until their owning-domain gates pass, so a removed type withdraws surfaces, never records.
- **AC-IDA-08 — Invite/assert/end membership:** Given Prospective current authority requires an invitation issued by a capable organization actor and acceptance by the invited person, who must first accept the current governance terms version; a historical tenure may instead be asserted with provenance and no acceptance; end-now requires a current confirmed tenure and a retroactive end additionally requires counterpart confirmation, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Prospective current authority requires invitation and acceptance; historical tenure may be asserted and labelled. End-now is immediate; retroactive end requires counterpart confirmation, and (6) return Dated tenure/capacity periods persist; revoked authority is immediate; if the flow cannot complete, A rejected assertion is hidden publicly, its protected evidence retained and the dispute routed, and it grants no authority; a stale terms version returns 409 and requires renewed consent; a contested retroactive date is recorded as disputed without rewriting history while the current revocation stays immediate; an invited person who has not accepted the current terms remains pending with no authority and cannot be counted as a governance confirmer.
- **AC-IDA-09 — Create representation:** Given Both principal and representative parties exist and both confirm; at least one activity and one domain are named, territories are non-empty ISO-3166-1 alpha-2 codes or the sole `WORLDWIDE` sentinel, the end instant is after the start instant, `communicate` is granted separately, and any monetary authority carries an explicit ceiling amount and ISO currency, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Both parties confirm explicit activities, domains, territory, term, communication grant, and any monetary ceiling, and (6) return Authority begins only on acceptance and ends automatically on expiry/revocation; if the flow cannot complete, Authority begins only on acceptance, so a pending or rejected edge grants nothing and expiry or revocation ends it automatically; partially overlapping scope warns and coexists while identical overlapping scope requires explicit dual confirmation rather than a hard block; a null ceiling permits non-monetary scoped acts but fails every monetary act closed and escalates, and a currency mismatch is never implicitly converted.
- **AC-IDA-10 — Grant/revoke mandate:** Given The grantor holds the authority being delegated through a current active relationship, the requested activities, domains, term and ceiling are a subset of the grantor's own authority snapshot, and the command carries the aggregate ETag in `If-Match`, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) A capable holder grants a subset of their own authority; changes are plain-language, versioned, audited, and effective immediately, and (6) return Current authority projection refreshes; existing historic facts remain; if the flow cannot complete, A grant exceeding the grantor's authority, term or ceiling is refused by the database check against the grantor snapshot; when the grantor loses authority, dependent sub-grants revoke immediately while past valid actions remain attributable; revocation is immediate and commits revocation, authority-projection invalidation, audit and the context-revoked event atomically, and history and already-relied-upon actions survive.
- **AC-IDA-11 — Propose governance terms:** Given The proposer holds an eligible governance-proposal grant for the band, the draft is a complete immutable terms version carrying a document hash, and every current permanent member is identified as a required confirmer of that exact version; before activation the disclosed platform and legal defaults remain authoritative, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Draft immutable terms version; all current permanent members review the same hash/version, and (6) return Terms activate only after unanimous confirmation; otherwise prior/default rules remain; if the flow cannot complete, A proposed version's content and member set are immutable, so a member joining or leaving mid-vote freezes the proposal and requires a superseding version with a recalculated member set rather than a mutation; any rejection prevents activation and the prior or default rules remain; activation locks the proposed version, expected member set, all confirmations and the current active version in one RPC, so a stale confirmation returns a typed conflict.
- **AC-IDA-12 — Record name ownership:** Given The actor holds a current owner or admin grant for the band, the statement names owners and a disposition, and any trademark reference is self-supplied; the platform performs no search, clearance, verification or registration, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Record a versioned ownership/disposition statement and optional self-supplied trademark reference without legal verification or registry assurance, and (6) return Statement is attributable and dated; platform does not adjudicate ownership; if the flow cannot complete, The platform does not adjudicate ownership, so a competing statement is recorded and dated alongside rather than resolved; a superseding record supersedes but never deletes the prior statement; no legal conclusion, template advice or registry assurance is returned.
- **AC-IDA-13 — Use treasury authority:** Given The acting human holds a confirmed membership of the band to view its money records, and any authorizing act additionally requires a current mandate covering the activity and a declared monetary amount within its explicit or seeded ceiling, routed through the compliance-cleared single-payee payment boundary, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Every member can view band money records; action authorization reuses the current mandate and single-payee payment boundary, and (6) return No platform-held pooled balance or multi-party distribution is implied; if the flow cannot complete, A monetary act above the ceiling, in a mismatched currency or outside a current mandate fails closed and escalates; pooled funds, split routing, escrow, tax computation and multi-party payouts remain disabled, so a request implying a platform-held band balance is refused rather than approximated.
- **AC-IDA-14 — Close/dissolve/re-form party:** Given Closure requires the actor's current owner or admin grant with only finite resolvable obligations outstanding; dissolution of a band additionally requires a vote of current permanent members under the active governance terms, with former and non-member stakeholders notified but voteless unless an active recorded term explicitly grants a vote, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Closure waits only on finite resolvable obligations; dissolution follows active governance rules and preserves all work. Re-forming creates a successor party with lineage, and (6) return Terminal state and dispositions are recorded; no destructive reopen; if the flow cannot complete, Unresolved name, funds or rights do not block a terminal state — the party records explicit unresolved dispositions and its records remain accessible by policy; dissolution is terminal, so re-forming creates a successor party with lineage rather than reopening while an ordinary closed party may reopen; no work is deleted and no destructive reopen is possible.
- **AC-IDA-15 — Record external identifier:** Given The actor may act for the subject party, the namespace exists in the configured registry, the value passes that namespace's format and capacity validation, and provenance is recorded; a verification attempt additionally requires a configured, healthy registry adapter, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Validate namespace format/capacity, record provenance, and attempt configured registry verification, and (6) return Identifier is labelled `self_asserted|verified|mismatch|collision|revoked`; if the flow cannot complete, Registry unavailability preserves the local claim and prior evidence and marks verification delayed, never silently downgrading verified evidence; a provider result computed against a stale claim version is retained as attempt evidence but cannot transition state; a self-asserted, mismatch or collision label may display but cannot independently route royalties or prove ownership.
- **AC-IDA-16 — Resolve identifier collision:** Given An open identifier-collision row exists over the same namespace and normalized value with two or more live claims; resolution requires either a withdrawal by a claimant or registry-backed evidence, and the resolving command locks the claim and collision rows, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Hold both claims, suspend verified/routing status, notify both parties, and accept withdrawal or registry-backed resolution, and (6) return Exactly one claim may become routing-eligible; history remains; if the flow cannot complete, While the collision is open every involved claim loses verified and routing status and no winner is guessed; without withdrawal or registry-backed evidence the collision stays open and routing stays blocked; at most one claim may become routing-eligible and the full claim history remains.
- **AC-IDA-17 — Nominate legacy successor:** Given The nominator is a living, active person acting as self, the nominee is an existing or invited person, and any prior active nomination by that nominator is superseded — exactly one nomination is active per person and the record is private, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Living user privately nominates an existing or invited person; nomination is evidence, not probate authority, and (6) return Versioned nomination is revocable while the nominator is alive; if the flow cannot complete, A nomination is evidence, not probate authority, so it confers nothing during life and by itself grants no administration on death; it is revocable only while the nominator is alive; a version conflict against a concurrent nomination returns a typed refusal with no lost update.
- **AC-IDA-18 — Report death/memorialise:** Given A report opens a protected case with evidence references restricted in Storage; any public, session or authority change additionally requires the counsel-approved evidence policy to verify that case, and estate administration additionally requires verified legal authority, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Open a protected case; no public/auth change occurs until the counsel-approved evidence policy verifies the report, and (6) return Authority ends, public party becomes memorialised, and scoped estate representation may begin; if the flow cannot complete, A false or unverified report produces no public or authority change, is rate-limited and routes to protected review, and a verified case that is later reversed returns to active through the protected false-report runbook with audit; a death with no successor revokes the deceased's authority, preserves earnings and rights records and leaves the party ownerless and unadministrable until verified legal authority exists; no login, signature or attestation as the deceased is ever possible.

### Global Interaction Rules

- Every command inherits Shard 00 validation, idempotency, optimistic concurrency, error, audit, outbox, and accessibility contracts.
- One authenticated human acts as exactly one party per command. Subject party, beneficiary, recipient, or represented party are separate explicit fields.
- Acting context is bound when an interaction opens and revalidated at submit. A stale/expired mandate cannot commit even if the UI still displays it.
- Reattribution is forbidden. A wrong-context relied-upon fact is retracted/tombstoned and re-created under the correct actor.
- Third-party reliance controls reversibility: money/attestation 0 seconds; communication/publication 60 seconds; private state until another party relies.
- A command that requires step-up and finds no fresh proof stops before any state change and returns the typed step-up-required refusal; the interrupted context is restored after step-up, and the command is re-confirmed by the human, never replayed automatically.
